# CYDRA Semantic Interaction and Toolchain Contract

## Purpose

CYDRA's reasoning contract is project-independent. Compiler, parser, AST provider, execution engine, and other external tools are replaceable capabilities used to generate evidence for that reasoning contract.

## Toolchain discovery before evidence generation

Before selecting an evidence-generation capability, CYDRA must discover the target project's declared environment. Relevant evidence includes project instructions, README/build instructions, build configuration, CI configuration, lockfiles, compiler pragmas, dependency metadata, and other explicit toolchain declarations.

CYDRA must distinguish:

- **Declared environment** — the toolchain/version/configuration the project says it expects.
- **Observed environment** — the capability and configuration CYDRA actually has available or provisions.
- **Substituted environment** — an observed capability intentionally used instead of the declared one.

A substituted capability may be used when necessary, but its compatibility and fidelity must be established and recorded before evidence generated by it can support a security claim. A toolchain mismatch is an observation, not permission to silently weaken evidence requirements.

Capability failure must not collapse the reasoning flow. CYDRA may continue with partial understanding where the evidence supports it, but it must preserve unresolved state and must not label approximate or incomplete evidence as compiler-faithful verification.

## Semantic interaction composition

Canonical AST-backed relationships may be composed into semantic interactions only when the relationships share the required canonical identity and the evidence needed for the composition is present.

For function-local ordering, the minimum boundary is:

1. both relationships are evidence-backed and candidate relationships;
2. both relationships belong to the same canonical function declaration;
3. both relationships have usable source locations;
4. the source locations establish the relevant **syntactic/source ordering**.

Missing ordering evidence, conflicting function identity, or cross-function relationships must not be composed into a security interaction.

### Syntactic ordering is not runtime causality

A Solidity AST source range identifies the source-code range represented by an AST node. Therefore source offsets can establish syntactic ordering. They do **not**, by themselves, prove that one operation executes before another on every runtime path.

CYDRA must keep these claims separate:

- `syntactically_ordered` — supported by canonical source-location evidence;
- `runtime_causally_ordered` — requires control-flow or execution evidence sufficient to establish runtime ordering.

A syntactically ordered interaction is a hypothesis-generation input, not a verified runtime causal claim. Runtime causality must be established separately before a security claim can be emitted.

## Evidence provenance

Semantic-interaction evidence should retain canonical function identity, AST node identity, source location, provenance, confidence, project revision, and toolchain identity where available. Source locations follow the compiler's source-mapping convention rather than filename or basename guessing.

## Reasoning boundary

The intended pipeline is:

`Declared environment → capability selection/provisioning → compatibility/fidelity assessment → canonical AST evidence → semantic relationships → semantic interactions → competing hypotheses → discriminating observations → verification → causal claim`

No step may silently convert a capability limitation into stronger evidence, and no semantic interaction may silently convert syntactic ordering into runtime causality.
